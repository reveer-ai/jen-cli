## Why

ENG-194 settled four things about the agent substrate — homogeneity, credentials inherited verbatim, an assistant reached through an adapter, and a thinking loop that is the runtime's rather than the assistant's — and left seven questions open. Six tasks are waiting on them: ENG-196 cannot provision a sandbox without knowing what a sandbox is, ENG-210 cannot expose a capability surface nobody has specified, ENG-211 cannot write an adapter interface without knowing what it must not be shaped like, and ENG-197, ENG-198, and ENG-212 all name this task as the thing that settles their mechanism.

This change settles them and writes down the reasoning, so that six tasks build against one architecture rather than six compatible-looking guesses.

Nothing is implemented here. The output is the artifacts: a capability stating what the substrate must satisfy, and a design document carrying why each answer is the one it is.

## What Changes

**The result that shapes everything else: there is no component outside the agent tree except the launcher.** Homogeneity requires that `spawn` be the runtime's own rather than a service a parent renders to its children — a root has no parent, so a parent-rendered capability is one the root could not have. It does *not* require a broker. Every runtime reaches the container driver directly, so root and depth-3 create sandboxes by identical code, and the only thing outside the tree is the entry point that creates the root's sandbox. The launcher is not privileged and is not a service: it calls the same driver every runtime calls, and is distinguished only by having no parent.

The seven questions, settled:

- **Sandbox mechanism** — one provisioning interface with drivers behind it. A local Docker driver is the first real one; an in-process driver runs the substrate's own tests with no daemon, so ENG-199 costs nothing to iterate on and runs in CI. A hosted provider becomes a third driver rather than a rewrite. Each runtime holds the container socket, which is what lets it spawn without a broker. That socket is root-equivalent on the host, and the design states plainly why that is accepted rather than mitigated: an agent already holds the run's credentials verbatim by ENG-194's decision, and already runs a coding assistant in auto-permission mode. The threat model is already that these agents are trusted; the socket does not widen it.
- **Filesystem** — every agent gets a private workspace, a fresh volume mounted at a fixed path and destroyed with the container. **No host directory is mounted in**, which is what makes ENG-196's "no credential on disk" true by construction rather than by cleanup. Credentials arrive as environment. Children do not share a parent's workspace: concurrent agents would clobber one another, and a shared mount is the first thing to break under a remote driver. Work travels back in ENG-212's result envelope. When two agents eventually need the same repository, the sharing mechanism is git — ENG-200's hosted backend, where a child clones and pushes a branch — and the substrate should not invent a second one that git will replace.
- **Persistence** — fresh per invocation. A sandbox lives exactly as long as the agent in it. ENG-196's "leaves nothing behind", ENG-212's teardown-on-completion, and ENG-199's clean-exit criterion already assume this; persistence would need identity, reattachment, and garbage collection, and nothing in the epic needs what that buys.
- **Capability surface** — capabilities are the tools the runtime's thinking loop presents to the model. A capability declares a name, an input schema, an invocation, and optionally a stream; the runtime holds a registry of them and knows that shape and nothing more. An empty registry is valid, which is exactly ENG-210's test — an agent that thinks and does nothing else. MCP does not appear on this surface: it belongs to the *assistant's* toolset, one layer down.
- **Language** — TypeScript, and not because the CLI already is. The substrate is container orchestration and process supervision, which is Go-shaped work: a static binary, a Go-native Docker SDK, better supervision and cancellation primitives than the SIGTERM handling in `cli/exec.ts` today. What decides against it is that **the sandbox image carries Node regardless**, because Claude Code is a Node CLI running in the agent's sandbox as a child process of the runtime. Go's binary-size advantage — the one argument specific to this workload rather than generic — buys a small binary sitting beside a full Node install, and its startup edge is milliseconds against an agent whose first act is a model call. What remains is shared types with the frontend jen is becoming, and one toolchain across CLI, backend, and UI. The decision would flip if the assistant ran in its own container, which is why the design records that as the condition rather than leaving it implicit.
- **Model access** — the loop reasons through an OpenAI-compatible chat-completions client with a configurable `baseURL`, so OpenRouter, Anthropic, or anything else is a config value rather than a vendor commitment; the compatible surface is the seam, with no abstraction of our own on top of it. Two credential slots, as ENG-194's definition of an agent already implies, both inherited verbatim. They are two because the loop's provider and the assistant's are plausibly **different vendors entirely** — an OpenRouter key for one, an Anthropic key for Claude Code — and neither slot knows anything about the other. A specific instance worth recording: `cli/github.ts:94` accepts a `CLAUDE_CODE_OAUTH_TOKEN` today because Claude Code is what spends it, and that form will not serve a loop calling an API directly. Model ids are separate config fields per slot.
- **The assistant adapter** — `start(request)` returns a handle carrying progress, a result, and a stop. The interface is specified by what it must *not* contain: no MCP, no `-p`, no `stream-json`, no session id, no Claude Code vocabulary anywhere on it. Tools are described abstractly and the adapter translates. A test double and the Claude Code implementation are both required, and the double is the only real evidence the interface isn't Claude-Code-shaped.
- **Recursion bounds** — depth and fan-out, enforced at spawn, and **no spend ceiling**. Depth is data carried in the config, incremented by the child, with a maximum that is inherited and never raisable. Fan-out is cumulative per agent, not concurrent, because cumulative is what stops a loop. No run-level backstop: the two bounds already cap the tree — depth 2 at fan-out 3 is at most thirteen containers — so a third mechanism would guard a case that cannot arise.
- **Communication** — every runtime listens on an address; `spawn` returns the child's; sending is a request to an address. Parent and child are both addresses, so there is no upward and no downward, which is what ENG-198 requires. Visibility is by knowledge of an address rather than by an access list: an agent holds its parent's and those of the agents it spawned, and a sibling's only if someone sent it one. Two agents spawned by a third talk because the third passed each the other's — one code path for all three relationships. Addresses are unguessable, and each agent also carries an id minted at construction, because credentials inherited verbatim no longer identify anyone and attribution needs something that does.
- **Orphans** — every container is labelled with its run at creation, and teardown sweeps by label. This is what covers a parent dying before the agents it spawned, and it is a filter on a container list rather than a service that watches the tree.

**A consequence for ENG-197.** Its description has it enforcing "depth, fan-out, and spend". Spend is deliberately deferred, so ENG-197 enforces two bounds, not three. The design records why, so the omission reads as decided rather than forgotten.

**A consequence for ENG-211.** The assistant adapter's result carries usage even though nothing enforces a spend ceiling yet. The field is there so that adding one later is a change to `spawn` rather than a change to every adapter implementation — the cheapest possible hedge, taken because the alternative revises an interface whose whole point is stability.

## Capabilities

### New Capabilities

- `agent-substrate`: the architecture six tasks build against — what an agent is and why nothing but the launcher sits outside the tree, the sandbox contract and its driver seam, what an agent's filesystem is and what it is not, the shape of the runtime's capability surface, the two credential slots and why they are two, what the assistant adapter must and must not expose, how depth and fan-out are bounded and where, and how agents address one another.

A note on what this capability is for. It states the constraints every implementing task must satisfy, not the behaviour each one implements: ENG-196 will add what provisioning does, ENG-197 what spawning does, and so on. A requirement belongs here only if violating it would break homogeneity or leave two tasks building incompatible halves.

### Modified Capabilities

None. The substrate stands alone by ENG-194's scope decision — it is not wired into the dispatcher, does not replace the six stage skills, and touches no existing capability's requirements.

## Impact

- **No code changes.** This change is artifacts only.
- **Constrains** ENG-196 (sandbox), ENG-197 (spawn and bounds), ENG-198 (messaging), ENG-210 (runtime and capability surface), ENG-211 (assistant adapter), ENG-212 (lifecycle), and ENG-199 (the acceptance run).
- **Prior art it generalizes:** `cli/exec.ts` `#session` and `#clone` become the shape of one driver and one adapter; `cli/github.ts`'s `credentialsFor` and its one-of-two model credential rule become the two-slot config.
- **New dependencies:** a container runtime on the machine running the substrate, for the Docker driver only — the in-process driver keeps the test suite free of it — and an OpenAI-compatible client library for the loop.
- **A stated limit:** tool calling is the part of the OpenAI-compatible surface that varies most across providers, and the capability surface is entirely tool calls. Model choice is constrained to models with solid tool-call support, which the design records as a known limit rather than leaving to be discovered.
- **Adjacent, not touched:** ENG-203 carries repo authority as a per-agent capability with a monotonicity rule. The substrate integrates no git backend and so enforces no such boundary; this change states that boundary's absence rather than pretending to hold it.
